# 通用 Record Type 设计（与模型一致）

状态：设计已确认（见第 15 节），待按第 17 节顺序实现。

## 0. 核心原则

**记录类型（record type）是模型的一个"变体"，它拥有与模型相同的元数据：访问权限、记录规则、视图、菜单、动作、默认值。** 管理员对类型的配置，使用与配置模型相同的界面和相同的数据结构。

区别只有一点：类型的元数据是"限定在某个类型上"的。例如，药店模型的一条访问行是"对所有药店生效"，药店的"连锁总店"类型的一条访问行是"只对连锁总店生效"。

## 2. 一致性矩阵：模型 vs 类型

| 元数据 | 模型（现有） | 记录类型（本设计） | 类型上的限定方式 |
|---|---|---|---|
| 定义 | `ir.model` | `ir.record.type`，`model_id` 指向所属模型 | — |
| 字段 | 模型字段 | 与模型共享，类型不增减字段 | — |
| 对象访问 | `ir.access`（无域） | `ir.access` 增加 `record_type_id`，有值则只对该类型生效 | 访问行的 `record_type_id` |
| 记录规则 | `ir.access`（带 `domain`） | 同左，并且规则自动带上类型条件 | 访问行的 `record_type_id` |
| 视图 | `ir.ui.view`（按模型） | `ir.ui.view` 增加 `record_type_id`，有值则只用于该类型 | 视图的 `record_type_id` |
| 菜单 | `ir.ui.menu` | `ir.ui.menu` 增加 `record_type_id`，有值则是该类型的入口 | 菜单的 `record_type_id` |
| 动作 | `ir.actions.act_window` | 类型的动作带默认类型上下文和域 | 动作的 `context`、`domain` |
| 默认值 | `ir.default` | `ir.record.type.default`，按组 | — |

结论：类型不是新的"功能"，而是在现有元数据上增加一个**可选的限定字段** `record_type_id`，并把 `ir.record.type` 作为配置入口。

## 3. 数据模型

### 3.1 `ir.record.type`：类型定义

| 字段 | 类型 | 说明 |
|---|---|---|
| `model_id` | Many2one `ir.model`，必填，`ondelete='cascade'` | 所属模型 |
| `code` | Char，必填 | 编码，`(model_id, code)` 唯一 |
| `name` | Char，必填，可翻译 | 名称 |
| `sequence` | Integer，默认 10 | 顺序 |
| `active` | Boolean，默认真 | 停用后不能新建或切换到该类型；已有记录的访问行保留 |
| `parent_id` | Many2one `ir.record.type` | 父类型，同模型；见第 8 节 |
| `access_ids` | One2many `ir.access`，`record_type_id` 为本类型 | 本类型的访问行（对象权限和记录规则），可直接编辑 |
| `view_ids` | One2many `ir.ui.view`，`record_type_id` 为本类型 | 本类型的视图，可直接编辑 |
| `menu_ids` | One2many `ir.ui.menu`，`record_type_id` 为本类型 | 本类型的菜单，可直接编辑 |
| `default_group_ids` | One2many `ir.record.type.default` | 对哪些组是默认 |
| `allowed_group_ids` | 计算、存储 | 本类型访问行中出现的组，加上祖先类型的组（并集） |

约束：

- `(model_id, code)` 唯一；
- `parent_id.model_id` 等于 `model_id`，不允许循环；
- `access_ids`、`view_ids`、`menu_ids` 中的记录，其模型必须等于 `model_id`（访问行、视图）或菜单动作指向该模型（菜单）。

### 3.2 对现有模型的扩展（限定字段）

在现有的三张元数据表上增加一个可选字段，不改变已有行为：

| 表 | 新增字段 | 语义 |
|---|---|---|
| `ir.access` | `record_type_id`（Many2one `ir.record.type`，可空，索引） | 为空：对模型的所有记录生效（原有行为）；有值：只对该类型的记录生效 |
| `ir.ui.view` | `record_type_id`（Many2one `ir.record.type`，可空，索引） | 为空：模型默认视图；有值：该类型的视图 |
| `ir.ui.menu` | `record_type_id`（Many2one `ir.record.type`，可空，索引） | 为空：普通菜单；有值：该类型的入口菜单 |

约束：有 `record_type_id` 的行，其 `model_id`（访问行）或模型（视图）必须与类型的 `model_id` 相同。

### 3.3 `ir.record.type.default`：每组默认类型

与 `ir.default`（F5）结构一致：

| 字段 | 类型 | 说明 |
|---|---|---|
| `model_id` | Many2one `ir.model`，必填 | 模型 |
| `group_id` | Many2one `res.groups`，必填 | 组 |
| `record_type_id` | Many2one `ir.record.type`，必填 | 默认类型 |

约束：`(model_id, group_id)` 唯一；`record_type_id.model_id` 等于 `model_id`；组属于该类型的 `allowed_group_ids`。

### 3.4 记录上的字段

支持类型的模型，记录上有 `record_type_id`（Many2one `ir.record.type`，`index=True`，`ondelete='restrict'`）。字段由类属性 `_record_type = True` 声明，由元类自动添加（F6）。自定义模型通过 `ir.model` 的开关生成同样的字段（F7）。

## 4. 开启

- **代码模型**：类上声明 `_record_type = True`，升级模块后添加 `record_type_id` 字段。
- **自定义模型**：`ir.model` 勾选"支持记录类型"，生成时设置同样的类属性，并创建手工字段（F7）。
- **关闭**：有记录引用类型时不允许关闭；关闭时类型的访问行、视图、菜单设为不活动，不删除。

## 5. 访问权限：与模型完全一致

### 5.1 用同一种方式配置

管理员在类型的"访问"页签中，像在模型上一样配置访问行：组、操作（`crud`）、域（记录规则）。这些行的 `record_type_id` 指向本类型，因此只作用于本类型的记录。

### 5.2 与 F2 的关系：模型级授权必须被类型级取代

对于支持类型的模型，非管理员组在模型上的**无域授权行**（`record_type_id` 为空、无域）会对所有记录生效，使类型的限定失效（F2 的 OR 语义）。因此：

- 对支持类型的模型，非管理员组的访问行必须带 `record_type_id`，不允许无类型的无域授权；
- 保存访问行时校验：如果模型已开启类型，且组不是管理员，则访问行必须指定类型；
- 开启类型时，生成一份清单，列出所有无类型的非管理员授权；管理员为每一条选择"归入某个类型"或"删除"，清单全部处理完才允许保存启用。

这条校验使"类型权限"成为唯一的非管理员授权来源。

### 5.3 记录规则

类型的记录规则就是该类型访问行中带 `domain` 的行，与模型的记录规则配置方式相同。规则域自动与类型条件 AND：实际生效的域为 `[('record_type_id', '=', T)] AND 规则域`。

### 5.4 没有授权的类型

类型没有任何授权行时，非管理员对其记录没有权限（F2）。这是本设计的既定规则：对非管理员不可见，避免新类型忘记配权限时记录意外暴露。类型页面应显示"无授权"的提示，帮助管理员发现这种情况。

### 5.5 管理员

框架不会让 `base.group_system` 自动绕过访问控制（F2）。开启类型时，为管理员组生成一条无类型、无域的授权行，保证管理员看到所有记录。

## 6. 视图：与模型完全一致

### 6.1 类型的视图

- 类型的视图是 `ir.ui.view`，`record_type_id` 指向本类型，`model` 为模型，`type` 为表单、列表等，与模型的视图相同；
- 类型视图的 `inherit_id` 可以指向模型的默认视图，`mode = 'extension'`，只写与默认的差异（F3）；
- 类型也可以有完整的独立视图（`mode = 'primary'`），与模型视图互不影响。

### 6.2 选择规则

视图由动作决定（F3）：

1. 类型的菜单动作指定 `view_id`（表单、列表）为类型视图；
2. 类型视图没有配置时，使用模型的默认视图；
3. 其他入口（相关字段、搜索等）使用模型默认视图。

同一条记录从不同菜单打开，视图可能不同，这是框架的限制（F3），需要接受。

## 7. 菜单与动作：与模型完全一致

### 7.1 类型的菜单

- 类型的菜单是 `ir.ui.menu`，`record_type_id` 指向本类型，结构与模型的菜单相同（名称、父级、顺序、组、动作）；
- 创建类型时，系统默认生成一个菜单（父级为模型的根菜单，动作为类型的默认动作），之后管理员可以像编辑普通菜单一样修改它，也可以删除或新增；
- 菜单的组默认取类型的访问组（读权限），管理员可以单独修改；F4 中菜单按组过滤，所以菜单的可见性仍由组决定。

### 7.2 类型的动作

- 类型的窗口动作（`ir.actions.act_window`）：`res_model` 为模型，`domain` 为 `[('record_type_id', '=', T)]`，`context` 为 `{'default_record_type_id': T}`；
- 默认菜单指向默认动作；管理员新增的菜单可以指向任何动作，包括模型的通用动作。

### 7.3 同步的边界

- 系统只在创建类型时生成一个默认菜单和默认动作；之后的修改由管理员直接编辑，系统不覆盖；
- 停用类型时，类型的菜单设为不活动，不删除；
- 同步函数只写入变化的字段（F8）。

### 7.4 移动端

F4 中 `load_menus` 的缓存不区分设备，会让 PC 菜单出现在移动端。做法：先把设备类型加入 `load_menus` 的缓存键，作为独立的小改动单独评审和提交；修复完成后再做移动端的类型菜单。修复不依赖 record_type 功能，PC 的开发不被阻塞。

## 8. 继承

类型继承（`parent_id`）只用于两件事，其余不继承：

- **视图**：子类型的视图可以把父类型的视图作为 `inherit_id`，形成扩展链；
- **默认值**：默认类型的选取规则按用户组独立计算，不依赖父子关系。

**访问权限不继承。** 每个类型只配置自己的访问行，子类型不会自动获得父类型的组，父类型的访问也不会传给子类型。理由：访问权限是最需要显式可见的元数据，自动继承或复制都会让管理员看不清"某组到底能看哪些类型"。Salesforce 的 Record Type 也不继承权限。因此不再需要"冗余访问行"或"域中列出父子类型"两种方案。

菜单和动作同样不继承，每个类型各自配置。

## 9. 默认类型

与 `ir.default` 的方式一致：

1. 取用户有效组（F1）；
2. 在 `ir.record.type.default` 中查找这些组对该模型的默认；
3. 多个组给出不同默认时，取 `sequence` 最小的；
4. 没有默认时，取用户有权使用的第一个类型；
5. 没有可用类型时不设默认，保存时报错。

只选用户有权使用的类型，避免默认指向无权的类型。

## 10. 创建类型的来源

1. **管理员界面创建**：在类型定义界面新建，然后在各页签中配置访问、视图、菜单、默认值。这是主要入口，与配置模型的方式相同；
2. **模型启用时**：如果模型已有记录，必须自动创建一条默认类型（权限为空，只有管理员可用），把现有记录归入，否则 `record_type_id` 无法设为必填；如果模型没有记录，不自动创建，由管理员决定；
3. **模块预设**：模块可以随附类型数据，放在 `<data noupdate="1">` 中，只在安装时创建，之后由管理员维护（F8 与升级覆盖的问题，见 13.2 节）；
4. **迁移**：pharaccount 的旧数据通过一次性迁移脚本转换。

## 11. 管理界面

类型的界面与模型的技术配置界面一致，使用页签：

- **概览**：模型、编码、名称、顺序、父类型、启用状态；
- **访问**：访问行列表，可新增、编辑、删除，与模型的访问页签相同；
- **记录规则**：访问行中带域的部分，同访问页签，单独显示；
- **视图**：类型的视图列表，可以新建扩展视图或独立视图；
- **菜单**：类型的菜单列表，可以新增、编辑、删除；
- **默认**：每组的默认。

## 12. 生命周期

- **创建类型**：创建记录，生成默认菜单和默认动作；
- **修改类型**：编辑访问、视图、菜单的行本身，类型的父子关系变化时只更新计算字段；
- **停用**：类型设为不活动，表示不能再新建或切换到该类型。访问行保留，已有记录对原来的组仍然可见；如需收回权限，由管理员显式修改访问行。菜单设为不活动；
- **删除**：只有没有记录引用、并且没有子类型时才允许删除，删除其访问行、视图、菜单；
- **关闭模型的类型支持**：有记录引用时不允许。

## 13. 风险与注意

### 13.1 启用时的访问切换

对已有模型启用类型时，非管理员的无类型授权会失效（5.2）。启用流程必须先生成清单，由管理员逐条处理，全部完成后才允许启用，否则启用后要么看不到数据，要么权限不生效。

### 13.2 升级覆盖

管理员在界面里改的访问行、视图、菜单，如果它们也来自模块数据文件（不带 `noupdate`），升级会覆盖（F8 相关的数据重载）。所以模块随附的类型数据必须带 `noupdate="1"`；管理员改动的记录由系统标记为"手工"，升级不覆盖。

### 13.3 性能

访问行、视图、菜单增加了一个可空字段，已有查询不受影响；`record_type_id` 要建索引。记录规则的域增加了一个等值条件，代价可接受。

## 14. 迁移 pharaccount

1. `pharaccount.account` 声明 `_record_type = True`，升级后 `record_type_id` 字段出现，允许为空；
2. 迁移脚本：
   - 把 `pharaccount.record.type` 转为 `ir.record.type`，`model_id` 为 `pharaccount.account`，`parent_id` 映射；
   - 把原来的组转为类型的访问行（每个组、每个类型，`crud` 按原权限）；
   - 把 `pharaccount.account.record_type_id` 映射到新类型；
   - 把模型上的无类型授权（如 `access_pharaccount_account_user`）替换为类型授权，否则类型限定失效（5.2）；
   - 对没有组的类型，保持无授权（对非管理员不可见），由管理员补齐；
3. 生成默认菜单和默认动作；
4. `record_type_id` 改为必填；
5. 旧的 `pharaccount.record.type` 保留一个版本只读，然后删除。

迁移写入会更新 `write_date` 和 `write_uid`（F8），在迁移说明中记录。

## 15. 已确认的决定

1. **没有授权的类型**：对非管理员不可见（5.4）。
2. **停用后的可见性**：停用只阻止新建和切换，已有记录对原来的组保持可见（12）。
3. **继承**：不做访问继承，只继承视图扩展链（8）。
4. **启用时的无类型授权**：逐个确认，通过清单处理（5.2）。
5. **菜单**：每个类型默认生成一个菜单，管理员可删除或修改（7.1）。
6. **移动端**：先单独修复 `load_menus` 缓存键，再做移动端类型菜单（7.4）。
7. **默认类型**：模型启用时有记录则自动创建一条默认类型，无记录则不创建（10）。

## 16. 测试

- 元数据：`(model_id, code)` 唯一；父子同模型、无循环；访问行、视图、菜单的 `record_type_id` 与模型一致；
- 访问：类型访问行只作用于本类型；非管理员的无类型授权在支持类型的模型上被拒绝；管理员可见全部；
- 规则：类型规则域与类型条件 AND；
- 视图：菜单动作使用类型视图；未配置时使用模型视图；扩展视图继承正确；
- 菜单：默认菜单自动生成；管理员修改不被系统覆盖；停用后隐藏；按组过滤；
- 默认（9）：只选用户有权的类型；多组冲突取 `sequence` 最小；
- 生命周期（12）：删除有记录时被拒绝；停用后访问行保留；
- 迁移（14）：迁移前后每个用户可见的记录数一致；
- 升级（13.2）：带 `noupdate` 的类型数据不被覆盖；管理员修改保留。
